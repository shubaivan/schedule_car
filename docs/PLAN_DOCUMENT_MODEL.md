# «План»: модель документа (проект, 16.11.2026)

Основа для розмови з Олександром про «логіку проведення» (ТЗ §2, §6, §8, §22).
Коду документів ще немає. Контрагенти (`counterparty`), на які документ посилається, вже є (гілка `feature/plan-counterparties`).

## 1. Що таке документ у «Плані»

Документ — це те, що **змінює облік**: залишки, борги, оплати. Рахунок, видаткова накладна, прибуткова накладна, повернення, акт, інвентаризація.
Задача (угода) і заявка на постачання документами не є. Це робочі процеси, де документ народжується і обговорюється.
Рух складу (`wh_movement`) сьогодні працює як спрощений документ без статусів. Пізніше він стане видом документа «складський рух» за цією ж моделлю.

## 2. Спільні поля (шапка `document`)

| Поле | Тип | Навіщо |
|---|---|---|
| `id` | int | |
| `kind` | varchar(24) | вид: `invoice` рахунок, `sale` видаткова, `receipt` прибуткова, `return_in`, `return_out`, `act`, `inventory`… Довідник `document_kind`: префікс номера, чи потрібне погодження, хто проводить |
| `organization_id` | int NOT NULL → `organization` | **наша** юрособа, від якої документ (якщо на заводі їх кілька, ТОВ + ФОП). Поки відповіді на питання 1 немає — одна організація з id 1 |
| `number` | varchar(32) | `РАХ-2026-000123`, див. §6 |
| `doc_date` | date | дата документа (саме вона визначає рік нумерації й період обліку) |
| `status` | varchar(12) | `draft` / `approved` / `posted` / `reversed` / `cancelled` |
| `counterparty_id` | int NULL → `counterparty` | клієнт або постачальник |
| `contract_id` | int NULL → `contract` | договір, коли з'являться «договори light» |
| `task_id` | int NULL → `task` | угода/задача, у чаті якої документ обговорюють |
| `author_id` | → `telegram_user` | хто створив |
| `approved_by/at`, `posted_by/at`, `reversed_by/at` | | хто і коли переводив стан |
| `reversal_reason` | text NULL | обов'язкова причина сторно |
| `currency` | char(3) | `UAH` за замовчуванням |
| `total`, `vat_total` | numeric(14,2) | підсумки рядків, рахуються сервером |
| `note` | text NULL | |
| `posted_hash` | char(64) NULL | sha256 шапки й рядків у мить проведення, щоб довести незмінність |
| `external_code`, `external_number` | NULL | код і номер з 1С при імпорті, для звірки |
| `version` | int | оптимістичне блокування: дві людини не перезапишуть одна одну |
| `created_at`, `updated_at` | | |

Рядки — одна таблиця `document_line`: `document_id, line_no, item_id NULL → wh_item, title, quantity numeric(14,3), unit, price, vat_rate, amount, site_from/site_to NULL`.
Особливі поля конкретного виду (номер авто для відвантаження, ПІБ водія) лежать у `attrs jsonb` і перевіряються класом виду.
Окрема таблиця на кожен вид документа не потрібна: 1С саме цим і важка.

## 3. Стани

```
чернетка ──погодити──▶ погоджено ──провести──▶ проведено ──сторно──▶ сторновано
   │                                  ▲
   └─────────────провести─────────────┘   (вид без погодження)
   └──скасувати──▶ скасовано
```

| Перехід | Хто (можливість PlanAccess) | Що відбувається в одній транзакції |
|---|---|---|
| створити / змінити чернетку | автор або `documents.edit` | номер видається при першому збереженні (§6); правити можна все |
| погодити | `documents.approve` (директор) | лише якщо вид вимагає погодження; документ стає тільки для читання, крім «повернути в чернетку» |
| повернути в чернетку | той, хто погодив, або директор | з причиною в стрічці |
| **провести** | `documents.post` (бухгалтер, директор) | `SELECT … FOR UPDATE` шапки, **картки контрагента** (два документи одного клієнта не пройдуть перевірку ліміту одночасно) і рядків залишків, яких торкаються рядки → перевірки (залишки на місці, кредитний ліміт і відстрочка контрагента, закритий період) → записи регістрів (§5) → `status=posted`, `posted_hash` → подія `StatusChanged` у `plan_event` |
| **сторно** | `documents.reverse` (бухгалтер, директор), причина обов'язкова | ті самі записи регістрів з протилежним знаком і посиланням `reversal_of` → `status=reversed`, `reversed_by/at`, `reversal_reason` → подія `SubjectClosed`. Шапка й рядки не змінюються і не видаляються |
| скасувати | автор або `documents.edit` | лише чернетка; номер лишається зайнятим, тому дірок у нумерації немає; подія `SubjectClosed` |

**Виправити проведений документ = сторно + «Створити копію»** (нова чернетка з тими самими рядками й посиланням на оригінал).
Редагування «на місці» після проведення немає ніколи.

## 4. Незмінність

- Сервіс `DocumentService` не дає змінити шапку чи рядки документа в стані `posted`/`reversed`.
- Захист і на рівні БД: тригер `BEFORE UPDATE` на `document` пропускає для `posted` лише перехід у `reversed` разом із полями сторно (`reversed_by/at`, `reversal_reason`) і службовими `updated_at/version`; для `reversed` і `cancelled` — нічого. Тригер `BEFORE UPDATE OR DELETE` на `document_line` і `register_entry` для проведених документів кидає `DOCUMENT_POSTED_IMMUTABLE`. Так зроблено і в PMAP (`accounting_postings_no_update`).
- `posted_hash` перевіряє команда `plan:documents:verify` (нічний cron, як контрольні суми файлів).

## 5. Регістри (що саме «проводиться»)

Проведення пише рядки в журнал регістрів `register_entry`: `document_id, register (stock | settlement), sign (+1/−1), item_id/site_id, counterparty_id, contract_id, quantity, amount, occurred_on, reversal_of_id`.
- `stock`: залишок позиції на місці. Сьогоднішній `wh_balance` стає проєкцією цього регістру.
- `settlement`: взаєморозрахунки з контрагентом (борг клієнта / наш борг постачальнику). З нього рахуються «борг», «прострочено за відстрочкою» і «вільний кредитний ліміт» у картці контрагента.
Залишки й борги рахуються з регістрів і ніколи не редагуються руками. Це та сама ідея, що в 1С, без її конфігуратора.

## 6. Нумерація

- Таблиця `document_sequence(organization_id, kind, year, prefix, last_number, padding)`, PK `(organization_id, kind, year)`.
- Номер видається в транзакції збереження через `INSERT … ON CONFLICT (organization_id, kind, year) DO UPDATE SET last_number = document_sequence.last_number + 1 RETURNING last_number` (перший документ року створює рядок). Рядкове блокування Postgres дає без дублів навіть при одночасних збереженнях.
- Формат `<ПРЕФІКС>-<РІК>-<000123>`, рік = рік `doc_date`. Унікальність `(organization_id, kind, number)`.
- Номер дається при першому збереженні чернетки, бо рахунок клієнту потрібен з номером одразу. Скасована чернетка номер не звільняє.
- Після видачі номера рік `doc_date` змінити не можна (дату в межах року — можна). Інший рік — нова чернетка («Створити копію»), інакше номер мав би чужий рік.
- Документи з 1С зберігають свій номер у `external_number`, а наш номер отримують окремо.

## 7. Зв'язок із задачею-чатом і стрічкою подій

- Документ — новий тип суб'єкта `SubjectType::Document` (`document-123`). Кожна дія — рівно одна подія в `plan_event` у тій самій транзакції (`SubjectCreated`, `SubjectUpdated`, `StatusChanged` from→to; сторно й скасування — `SubjectClosed`, як закриття задачі; `StatusEvent::for` обирає клас сам). Звідти, як для задач і складу, живляться Хроніка, сповіщення, пошук і аудит.
- Картка документа має свою стрічку (той самий `TaskChat`: події + коментарі), як картка позиції складу.
- `task_id`: документ, створений з угоди, з'являється в її чаті системним повідомленням «Створено рахунок РАХ-2026-000123 на 48 000 ₴» з посиланням. Проведення й сторно теж пишуться в чат задачі.
- Картка контрагента показує його документи й борг (з регістру `settlement`).

## 8. Аудит

- `plan_event` вже є журналом аудиту (сторінка суперадміна `/crm/admin/audit`). Доменні події документів не підпадають під прибирання (`PLAN_AUDIT_RETENTION_DAYS` стосується лише службових).
- Для `SubjectUpdated` чернетки у `payload` пишемо змінені поля зі старим і новим значенням, щоб було видно, хто змінив ціну.
- Перегляд і друк проведеного документа пишемо як `SubjectViewed` / `FileDownloaded` (вже є для файлів).

## 9. Питання до Олександра (логіка проведення)

1. Скільки юросіб відвантажує й купує (ТОВ, ФОП)? Від цього залежить, чи нумерація окрема для кожної.
2. Які документи потрібні першими: рахунок, видаткова, прибуткова, повернення?
3. Для яких видів потрібне погодження директора перед проведенням?
4. Хто проводить: лише бухгалтер чи й менеджер (відвантаження)?
5. Перевищення кредитного ліміту чи прострочена відстрочка: забороняти проведення чи лише попереджати, а директор дозволяє?
6. Закриття періоду: з якої дати не можна проводити й сторнувати «заднім числом»?
7. Сторно: лише в тому ж місяці чи будь-коли (тоді сторно датується сьогодні)?
8. Податкові накладні й реєстрацію в ЄРПН поки лишаємо в 1С / M.E.Doc?

## 10. Порядок робіт

1. Контрагенти: зроблено, гілка `feature/plan-counterparties`.
2. Договори light: `contract(counterparty_id, number, date, valid_until, payment_terms, deferral_days, credit_limit, file)`.
3. Каркас документа: шапка, рядки, стани, нумерація, тригери, подія. Перший вид обираємо після відповіді на питання 2.
4. Регістри `stock` і `settlement`. `wh_movement` переходить на документ.
